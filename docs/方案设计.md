# AI 意图驱动问数工作流技术方案

> 当前架构以文末“LangGraph 单引擎修订”为准：LangGraph 为必需依赖。下文旧章节的双引擎描述保留作为历史决策，不再作为开发或验收要求。

## 技术方案概述

在现有 LangGraph/ScoredWorkflow 前端增加 AI 意图识别、意图校验、结构化检索条件构建和知识候选校验。知识库返回 Top N 候选后，现有 LLM 规划器结合原问题、结构化意图和候选知识生成逻辑计划，后续继续使用确定性 SQL 生成、安全校验、执行和结果评分。

完整设计见：`docs/superpowers/specs/2026-08-30-ai-intent-grounded-workflow-design.md`。

## 技术选型

| 类别 | 选择 | 理由 |
|---|---|---|
| 工作流 | LangGraph + ScoredWorkflow 降级实现 | 保持现有运行模式一致 |
| 意图模型 | 复用现有结构化 LLM 客户端 | 首版不增加部署复杂度 |
| 知识检索 | 结构化接口 + 本地加权召回 | 可测试，未来可替换 Qdrant |
| SQL | 确定性规则生成 | 防止模型编造表字段并保持安全 |

## 模块划分

| 模块 | 职责 | 依赖 |
|---|---|---|
| Intent Recognizer | 抽取用户原始意图 | LLM Client |
| Retrievability Validator | 按查询类型判断意图是否具备检索条件 | AgentState |
| Retrieval Query Builder | 生成结构化知识检索条件 | Intent |
| Knowledge Retrieval | 返回 Top N 企业知识 | Knowledge Client |
| Knowledge Validator | 判断候选是否可靠或需要澄清 | Knowledge |
| Grounded Planner | 结合原问题、意图与知识生成计划 | LLM Client |
| SQL/Execution/Result | 生成、校验、执行和评分 | 现有实现 |

## 关键设计决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 意图识别与知识检索顺序 | 先意图、后检索 | 避免直接用整句关键词匹配导致错误召回 |
| 意图模型是否决定正式指标 | 否 | 正式口径必须来自企业知识库 |
| SQL 是否由模型自由生成 | 否 | 保持确定性和安全边界 |
| 不可检索意图是否自动循环 | 否，生成澄清回答 | 没有用户新信息时重复调用没有增益 |
| SQL 重试范围（历史决策，已由 2026-10-11 修订替代） | 原为只重试 SQL 阶段；新路线按反馈返回对应决策节点 | 不再将原样重新生成 SQL 当作有效纠错 |

## 实现计划

1. 以 TDD 增加意图识别、校验与状态契约。
2. 以 TDD 改造结构化 Top N 知识检索接口。
3. 以 TDD 升级 grounded planner 与计划校验。
4. 重连 LangGraph 和 ScoredWorkflow。
5. 扩展追踪与 Debug 验证报告。
6. 运行全量测试并进行代码审查。

#### 1. 实施目标与边界

以“昨天香港开户人数，按开户渠道分别列出，并给总计”为贯穿案例。目标不是让模型多打一次分，而是明确：用户要求是什么、每项要求如何进入计划、实际 SQL 是否兑现、数据是否满足条件、答案如何引用结果。

首轮只覆盖现有指标和受支持维度。案例中的渠道若不受支持，应返回能力缺口，不新增渠道数据、不静默改为总计。相对日期以请求进入时固定的参考时刻及业务时区为准；例如参考日期为 2026-10-08、业务时区为 Asia/Shanghai 时，“昨天”为 2026-10-07。

方案比较：

| 路线 | 优点 | 限制 | 结论 |
|---|---|---|---|
| 继续调分数和阈值 | 变动少 | 检查语义不变，错误仍可高分通过 | 不作为主线 |
| 每一步交给模型复核 | 能处理部分开放语义 | 成本、时延、同源错误；无法证明权限和数据完整 | 不做默认路径 |
| 需求绑定＋程序规则＋选择性语义复核 | 大部分检查可重复，复杂疑点有补充审查 | 需要业务规则、证据和评测集 | 推荐，增量接入现有节点 |

不涉及 SFT/RL 训练，不承诺对任意自然语言、任意 SQL 做完备正确性证明。所谓验证通过，只表示在声明的业务范围及证据条件下通过规定检查。

#### 2. 用一条业务问题定义验收链

| 需求编号 | 用户原文 | 规范化需求 | 计划与执行检查 | 答案检查 |
|---|---|---|---|---|
| R1 | 昨天 | 请求参考日期的前一自然日 | 时间字段、边界及业务时区正确 | 显示实际查询日期 |
| R2 | 香港 | 地区筛选为香港 | 映射到正式维度成员和正确谓词 | 说明香港范围 |
| R3 | 开户人数 | 绑定正式指标及版本 | 按定义使用去重字段和状态条件 | 数值、指标名称与单位对应 |
| R4 | 按开户渠道分别列出 | 按渠道分组 | 受支持时包含分组；不支持则停止并解释 | 每个结果行绑定自己的渠道 |
| R5 | 并给总计 | 总计与明细两种输出 | 两种投影均存在并实际返回 | 两部分均展示 |

每项需求可以对应多个检查；不适用的阶段显式标记，不强迫所有需求在所有阶段都形成相同检查。

关键边界：给需求分配 ID 并不能证明需求清单完整。应保留原问题、原文位置和抽取前后的提案，检测常见条件线索与未解释片段；复杂问句、排除项、业务术语冲突触发原文对照复核。不能因为模型没有提取出某项，就认为用户没有提出。仍有实质歧义时澄清，不能虚构确定性。

技术选型：保留 Python、LangGraph（唯一工作流引擎）、现有 LLM Client、确定性 SQL 生成和模板回答。新增边界对象可用项目已声明依赖的 Pydantic 做结构验证；`AgentState` 保持 TypedDict，现有响应 dataclass 不必整体迁移。结构验证只保证类型和字段，不保证业务正确。

SQL 验证技术选型：用户提出 SQLGlot 偏重且选型尚未完成，因此撤回默认采用 SQLGlot 的建议。本版暂不实施 AST，不安装解析库；后续按依赖体积、运行开销、维护成本、方言支持及实际规则覆盖评估，另行确认。这是范围调整，不是已经通过性能测试得出的结论。

过渡期保留现有 SQL 基础检查、确定性生成、数据库只读权限和执行限制，继续核验生成前的计划与知识约束；不开放任意模型自由 SQL 执行。计划正确不等于实际 SQL 正确，字符串检查、模板生成或 EXPLAIN 均不能替代完整结构语义验证。未覆盖的查询应明确不支持或未验证，不把延后实现标为通过。生成器应使用独立预期及实际结果回归测试；暂缓的 SQL 风险单独记录，发布时披露。

占比特别处理：先明确分母定义，再复算。不能默认各分组去重人数相加就是全局去重人数；分组重叠或结果截断时，这个等式可能不成立。

#### 4. 公共数据结构与接口草案

以下均为拟新增或扩展的字段，不是当前 API 已有契约：

| 对象 | 关键字段 | 用途 |
|---|---|---|
| Requirement | id、kind、source_span、original_text、normalized_value、origin、required、resolution | 保留原文与明确/推断/默认来源；保留未支持和未解决项 |
| Binding | requirement_id、stage、target_ref、evidence_refs | 把需求连接到计划字段、SQL 节点或答案事实 |
| CheckResult | id、requirement_ids、stage、status、severity、expected、actual、evidence_refs、rule_version | 可解释的检查结果，而不只是数字 |
| ExecutionEvidence | execution_id、source、query_hash、snapshot/watermark、truncated、row_count | 区分查询结果与其完整性、版本条件；未知字段不能补猜 |
| Fact | fact_id、metric_id/version、dimensions、time_range、value、unit、execution_id、row_ref | 从真实结果构造，不由模型编造，供模板引用 |
| ReviewResult | stage、issue_type、requirement_ids、source_quote、evidence_refs、suggested_action | 记录模型提出的具体异议，不授予其最终放行权限 |
| Decision | outcome、blocking_check_ids、next_action、reason | 单一决策，驱动流程、API 和页面 |

拟新增 `agent/validation/`，按 contracts、requirements、plan_checks、sql_checks、result_checks、decision 分职责；模型审查使用单独的 reviewer 适配器。现有节点作为编排入口调用这些组件，避免校验逻辑复制到服务层。

内部接口建议为 `validate_*(context) -> list[CheckResult]`、`decide(required_checks, results) -> Decision`、`review(review_request) -> ReviewResult`。决定函数必须知道当前查询需要哪些检查，缺失结果不能借助空列表 all() 意外通过。

检查状态：PASS、FAIL、UNKNOWN、NOT_APPLICABLE；阶段另有 NOT_RUN。必须检查 FAIL 或 UNKNOWN 时不得生成“已验证答案”。歧义→澄清；不支持→能力说明；数据缺失→数据不完整；确定错误→阻断或定向修复。可选检查未知应披露，不误称全覆盖。

兼容策略：当前问答入口与 AskRequest 不变；AskResponse 增加有默认值的结构化验证信息并同步页面。迁移期保留旧 confidence/scores，标为旧规则分而非正确概率；页面与正文读取同一 Decision，不再各算阈值。具体英文 outcome 枚举及版本策略在 M1 评审冻结，不在此直接变更 API。

首版不新增数据库或管理平台；复用 request_id 和追踪存储，记录规则/知识/模型版本及必要证据引用。日志与复核输入脱敏，只保留授权范围内的必要材料。

#### 5. 按需模型复核的触发与约束

触发条件来自可解释规则，而不是“总分略低再问一次”：原文与需求清单有未解释片段；业务术语有冲突；复杂排除、比较或分母定义不能由程序确认；可选自然语言说明出现缺乏依据的结论。

审查分阶段进行：执行前审查原文—需求—计划的语义，执行后如允许开放式说明则审查事实—答案。两次不是默认都运行。首版只启用执行前的一次按需复核，事实主体使用模板；复杂答案审查作为后续开关功能。不得先执行仍有关键语义疑点的 SQL 再补做审查。

输入包括原问题、原文位置、需求清单、相关业务定义、程序检查以及适用阶段的事实；不让模型靠自己的长推理解释证明自己正确。要求返回具体遗漏、冲突、引文和引用 ID；程序验证引用确实存在且引用文字匹配，引用存在也不等于推断一定正确。

处置规则：提出可修复问题→形成候选修订并重新校验；真实歧义→问用户；程序已确认的硬失败→模型不能覆盖；缺数据水位或权限证据→模型不能补出“通过”。模型超时/输出非法时保留 UNKNOWN，关键问题不放行；只是可选文案润色失败可回退可信模板。简单且证据齐全的问题无额外复核调用。

模型意见是语义证据，不是正确性证明。即便换模型或调用多次，也不能把一致意见当作事实已证实。审查器先离线或影子运行，量化收益后再接入决策。

| M6 按需模型复核 | A/B/E 复杂语义增强 | 触发策略、结构化异议、预算与开关、无复核/有复核对比 | 在同一冻结集上有可接受净收益；不覆盖硬失败；失败路径可控 | 收益实验通过后接入 |

顺序为 M-1→M0→M1→M2→调整后的 M3→M4→M5→M6→v1.1.0。M-1 先保留修复前的最小复现与请求证据，再修复并回归；M0 扩充业务评测并区分修复前快照与修复后基线。M5 只表示基础验证阶段完成，不代表 v1.1.0 完成。M2 稳定后可以准备审查样本，默认决策接入仍以后续验收为准。模型复核按需触发，不意味着每个请求都调用；未通过收益与失败路径验收时，不能以关闭功能代替 M6 完成。

迭代数是工作拆分建议，不是工期承诺。需团队人数、熟悉程度、真实数据源/权限/水位获取情况才能换算日期。日历排期不得隐藏外部依赖：没有真实水位只可验收模拟接口；没有 Trino 环境不能宣称 Trino 集成已验收。

#### 7. 项目管理落地

以七类模块 A—G 作为长期工作域，以 M-1 和 M0—M6 作为交付阶段，以具体问题编号作为任务来源。M-1 是所有功能开发的最高优先级。任务不要命名成空泛的“提高准确率”，而应如“F03：上一轮 feedback 进入下一轮实际模型请求”。

每张任务卡必须包含：问题编号、用户原话/错误案例、影响、拟用技术、修改模块、依赖、责任人角色、正反例、验收证据、里程碑和回退方式。角色可兼任：业务负责人确认口径与标准答案；后端负责契约/检查/编排；数据负责人负责授权、元数据和水位；前端负责状态与证据展示；测试/评测负责人维护独立预期与对照报告。实际人员由团队分配。

示例任务卡 B03：

- 问题：llm_planner 丢掉知识不支持的渠道后，validator 只验证剩余维度。
- 方案：保留原始需求和提案，建立 R4→plan.group_by 绑定；不支持返回 UNSUPPORTED 语义，不生成替代总计。
- 依赖：M1 公共状态、M2 指标支持维度定义。
- 验收：明确要求渠道但不支持时停止；支持渠道时正常分组；未要求渠道时不误拒绝；LangGraph 工作流和 API 状态一致。
- 交付：代码、测试、带需求 ID 的验证报告、问题到证据的关联。

每个迭代按“选定问题与验收样本→先写失败测试→实现最小闭环→正反例验证→工作流/API/UI 演示→评测对比”推进。一个任务 Done 不等于里程碑完成，只有模块与外部依赖都完成验收才能退出里程碑。

测试分层：确定性单元测试；固定数据集成测试；真实模型语义评测；目标数据库集成测试。模型固定响应的测试不代表真实模型效果。参考结果不得由同一个待测 SQL 生成器自动充当标准答案。

共同验收指标：错误答案放行数/放行答案数、可回答题正确覆盖率、误澄清率、必需需求正确兑现率、修复成功及新引入错误、P95 耗时、模型调用与成本。无放行答案时错误率不可计算，不记为零。每阶段新增关键反例全部得到预期处理，同时原有正确用例无非预期退化。

M0 建立基线后、实施候选前冻结真实模型评测集、质量阈值和耗时/成本预算；不先承诺未经测量的 99% 准确率。模型复核先做影子对照，不影响用户结果；其硬失败处理与超时失败策略须单独验收。新机制通过验收后按受控开关接入，回退不得关闭已有安全约束或掩盖已知错误；必要时降级为停止回答。

下一步建议：先细化 M-1 的反馈链路任务及最小回归用例，再推进 M0＋M1；维持现有指标与支持维度的范围，不顺带扩大问数能力。尚未开始本路线的代码实施或作完成承诺。

#### 9. 2026-10-11 最高优先级反馈闭环与 SQL 范围修订

这里的 ReAct 指用户所说的“行动结果/反馈进入下一轮决策”，不是前端 React。当前仓库是固定节点工作流加 SQL 重试回路，不能声称已具备完整通用 ReAct 循环。

静态代码证据：SQL/结果校验器产生 `retry_feedback`；`create_retry_node` 只更新次数、动作并清空部分展示错误；反馈可以留在状态中，但 LangGraph 的 `retry` 回到 `sql_generator`，ScoredWorkflow 也只重跑 SQL 循环；`generate_sql` 不读取反馈，规划器 `model_input` 不含反馈且重试时未被重新调用。因此核心缺口是“保存了反馈，但下一轮决策没有消费”，不能仅增加 state 字段就认为修好。本次未运行缺陷复现或修改运行代码。

M-1 拟交付：

1. 保留请求内有界的轮次反馈记录，包含轮次、失败阶段、错误码/具体问题、上一轮计划/SQL、执行观察及必要上下文；原问题、知识口径和请求参考时间保持不变。
2. 将经过脱敏的最新反馈和必要历史显式加入下一轮规划/修复的实际模型请求；不能仅写日志或保存到 state。数据库返回及反馈作为不可信数据，不作为可改写权限或业务规则的指令。
3. 对可恢复的规划问题返回模型决策节点，消费反馈后输出结构化候选修订或明确停止原因，再由程序生成 SQL 并重验受影响阶段；不要求记录模型内部思维链，也不允许模型自由改写硬约束。
4. 不能修复的知识缺失、权限拒绝、数据未到齐直接停止或澄清。生成器自身的确定性程序错误不能靠原样重跑修好，应明确停止并报缺陷。传输类暂时故障单独有限重试。
5. 保持一次自动修复预算，修订产物没有有效变化且错误相同时停止；反馈属于当前请求，不能泄漏到其他请求。

M-1 验收：用可记录入参的测试模型构造首轮失败，断言第二次实际模型调用包含上轮错误、计划/SQL 和轮次；模型据此修订后相关检查重跑并成功或明确失败；无反馈首轮正常；错误不串请求；同产物不无限循环；LangGraph 与 ScoredWorkflow 结果一致。随后补真实模型场景验证，不能将测试模型成功称为真实模型效果。

M-1 解决已知反馈断链，M5 扩展修复覆盖与追踪，M6 才是按需独立模型复核，三者不能混为同一件事。SQL AST 暂缓不影响先修复反馈链；v1.1.0 最终版本目标不变。
