# M0 可复现业务评测基线：需求与设计规格

日期：2026-10-11（UTC+8）。状态：方案范围已在对话中确认；本规格待用户审阅后进入实现。

修订：2026-10-12，补齐问题编号来源和链接；用例统一采用 `M0-` 前缀；重新核对关联问题并明确单题覆盖边界。未改变 32 条场景或启动代码实现。

## 1. 目标与边界

建立固定业务考卷、独立标准答案和可重复运行的判卷工具。衡量当前 LangGraph 程序是否正确处理给定的模型输出、数据和故障，记录已知问题，供 M1—M6 比较。

- 唯一引擎为 `build_graph()` 返回的 LangGraph；不恢复 ScoredWorkflow。
- 默认完全本地：固定模型夹具、本地知识快照、隔离的 SQLite 内存库；不读取真实模型凭据，不访问 DeepSeek、Trino 或 Qdrant，不产生模型费用。
- 不实现 SQL AST，不修复当前时间理解、需求遗漏、结果评分或答案绑定缺陷。只增加必要的评测时间输入支持，且不改变未指定时间时的原行为。
- 不构建评测网页、在线评分服务或通用自然语言裁判，不声称真实模型准确率或生产数据库集成已验收。
- 当前基线标注为 `post-m1-langgraph-only`。保留旧 M-1 文档证据，不重新伪造历史运行；不因当前 Git HEAD 仍为旧版本就把工作区结果称为旧版本实测。

## 2. 功能需求与验收

| ID | 交付 | 给定—操作—预期 |
|---|---|---|
| M0-01 | 固定数据、时间、知识及元数据 | 给定同一用例快照，多次执行时业务状态、行集和判定一致；运行耗时等元数据除外 |
| M0-02 | 不少于 30 条独立业务用例 | 每题有唯一用例 ID、关联问题编号及覆盖说明、问题原文、输入、预期及预期依据；缺字段/重复 ID/错误引用使加载失败 |
| M0-03 | 单引擎批量入口 | 一条命令逐题运行真实 LangGraph；每题有独立状态、模型调用序列及数据库；禁止串用上题反馈 |
| M0-04 | 独立判定 | 程序即使自评 100%，只要日期、要求、结果或答案绑定错误，评测仍判 FAIL |
| M0-05 | 版本化报告及对比 | 逐题保存预期/实际/差异；分开记录业务失败与运行错误；只在兼容快照间给出可信前后对比 |
| M0-06 | 可验证的评测工具 | 用故意错误的观测结果验证判卷器能拒绝；连续两次执行比较确定性结果；原有回归不退化 |

M0 完成不要求业务题全部 PASS，但要求评测器自身测试通过、套件无未解释的运行错误、已知缺陷被准确标记。已知失败不能改成正确答案，也不能通过跳过用例或全部拒答掩盖。

## 3. 技术方案选择

采用“版本化 JSON 夹具 + 独立 Python 判卷器 + LangGraph 本地执行 + JSON/Markdown 报告”。复用项目 Python、Pydantic、SQLite 和 pytest，不新增依赖。

不选纯 pytest 断言堆叠：保留现有回归，但业务用例需可独立审阅、分类及生成对比报告。

不选首版真实模型批量评测：模型输出波动和费用会干扰程序基线。真实模型评测以后明确预算和样本后另行开展，当前入口不提供隐式联网开关。

## 4. 固定环境与数据

基准业务时区为 `Asia/Shanghai`，默认参考日期为 `2026-10-11`。时间边界题在各自用例内指定其他固定日期，不读取运行当天日期。

独立评测数据库从文本快照建立，表结构与当前两张演示表兼容；不使用按当天生成数据的 `SQLiteDemoClient._seed()`。建库后启用只读约束，逐题关闭连接；不访问或修改现有数据库。

开户主快照：2026-10-10 香港有 U1、U1、U2 三条 SUCCESS 和一条独立用户 FAILED；上海有 U3、U4、U5 三条 SUCCESS；北京有 U6 一条 SUCCESS。另有 2026-10-09 香港 U7、2026-10-11 香港 U8 两条 SUCCESS。用户 ID 在未注明跨日重叠时全局不同。

因此独立人工核算：10 月 10 日香港 2、上海 3、北京 1、全国 6；10 月 9 日总计 1；10 月 11 日总计 1；10 月 9—10 日去重总计 7。10 月 10 日互斥地区占比为香港 33.33%、上海 50%、北京 16.67%。这些值写为夹具字面量，不运行待测 SQL 生成器得到期望。

交易主快照：2026-10-10 香港两条 SUCCESS 金额 100.10、50.20 和一条 FAILED 金额 999；上海一条 SUCCESS 金额 200；北京一条 SUCCESS 金额 0。成功金额香港 150.30，全国 350.30。与开户表无 JOIN 要求。

时间边界题可使用明确列出的独立小快照；每份都带行级来源、人工核算说明和 SHA-256。知识为当前支持的开户人数/交易金额及地区/日期定义的独立副本，元数据从建成的 SQLite 读取核对，不从模型猜测。

规划器已有 `request_reference_date` 可复用。结果验证器的“今天”读取改为优先使用该请求参考日期，缺省仍使用原日期来源；此变更只固定时钟，不改评分阈值或 freshness 的业务含义。评测不通过全局篡改系统时间工作。

## 5. 首批 32 条用例

全部用例从 LangGraph 入口运行；每题标记 normal / model_fault / execution_fault / sql_fault 等输入来源。错误注入仅在评测进程内，不能成为线上请求参数。

### 5.1 编号来源与覆盖规则

问题编号来自 [《验证机制分类与里程碑》第 3 节](../../2026-09-29-验证机制分类与里程碑.md#problem-catalog)，沿用原定义，不在此重新编号。下方问题名称都是原定义的简写，点击可跳到对应原始条目。

- **用例编号**形如 `M0-A01`：表示 M0 的一道测试题。N 为正常查询、T 为时间、R 为需求与知识、S 为 SQL、D 为数据、A 为答案、F 为修复。
- **问题编号**形如 `A01`：表示问题清单里的“需求理解不完整”。`M0-A01` 与 `A01` 不是同一含义；例如用例 `M0-A01` 实际关联问题 `E01`。
- **功能需求编号** `M0-01` 至 `M0-06` 仍对应第 2 节的模块交付，不是业务用例。
- **正常回归**证明特定正确输入没有被改坏，不能证明对应问题已全面解决；**反例**检查某种具体错误是否被拦截。固定模型返回正确时间或歧义标记，不证明模型能自行识别时间或歧义。
- G01/G02 是整套评测工具的目标，放在套件级验收，不给每个正常查询重复贴标签。B02 在 M0 只覆盖固定知识/元数据快照；N01/N06 的普通查询不能证明知识 Schema 能拒绝错字段、非法聚合，因此移除这两处 B02 归类。

## 6. 模块与数据流

拟新增 `smart_ask_data/evaluation/`：

| 模块 | 职责 |
|---|---|
| cases.py | Pydantic 契约、加载及引用校验；不含被测节点逻辑 |
| sandbox.py | 固定模型响应序列、SQLite 快照、计数与限定故障注入，资源清理 |
| runner.py | 逐题创建 LangGraph、运行和提取观测；管理异常与执行预算 |
| judge.py | 基于独立预期比较需求、日期、结果、答案绑定、停止和修复证据 |
| report.py | JSON/Markdown 输出、快照指纹、稳定结果和历史对比 |
| __main__.py | 本地 CLI；不调用生产服务工厂或加载真实模型配置 |

数据放在 `data/evaluation/m0/v1/`：manifest、cases.json、knowledge.json、数据库文本种子及核算说明。首版从仓库根目录运行，不承诺脱离仓库的 wheel 资源分发。

路径：用例 + 快照 → 固定外部输入 → 真实 LangGraph/业务节点 → 观测 → 独立判卷 → 报告。判卷器不调用模型、不调用生产 SQL 生成器或答案检查器来决定预期。

故障注入边界：模型客户端返回显式序列；执行器模拟指定错误或异常行；SQL 反例在生成节点输出边界用限定的上下文替换注入候选，之后仍运行真实 SQL 校验与流程。每题结束恢复替换；逐题串行，不进行并发 monkeypatch。夹具耗尽、意外调用、错误注入未触发均报告运行错误，不能悄悄返回成功响应。

## 7. 用例与报告契约

用例至少包含 `id`、`category`、`issue_ids`、`coverage_note`、`question`、`reference_date`、`timezone`、`dataset_id`、`model_script`、`fault`、`expected`、`expectation_basis`。`id` 必须使用 `M0-` 用例前缀；`issue_ids` 引用原问题编号，`coverage_note` 明确是正常/停止/修复回归还是反例及其边界。G01/G02 在套件级记录，不自动加入每题；报告不把问题关联或正常题 PASS 当成整个问题已解决。输入与预期分区存储；异常不能仅通过自由文本随意执行 Python 代码。

预期至少明确允许的交付动作、必需需求（指标、日期、分组、过滤、总计/派生）、预期行或停止原因、是否允许执行 SQL、模型/SQL 调用预算；每项仅在适用题中必填。校验缺少预期行或停止理由的空壳用例。

逐题判定为 `PASS / FAIL / ERROR`：

- PASS：所有适用业务断言满足。
- FAIL：流程完成但存在具体业务差异，如错日期、负数放行、应答题被拒绝。known_issue 只是标记，不把 FAIL 变成 PASS。
- ERROR：用例/快照无效、依赖缺失、夹具序列不匹配、流程未捕获异常、评测器出错、预算超出；记录来源，不算成业务通过。

行比较采用规范化键（row_type、维度、日期）并检查重复、遗漏和额外行；只有题目要求排序时检查顺序。人数使用精确整数；金额/百分比容差显式为 0.005，拒绝 NaN/Infinity，不能因字符串转数字丢掉负号。

答案检查针对本套件受控表达：用独立的地区/指标/日期/数值绑定规则和必须/禁止事实检查模板或固定候选。无法判读的文本标注未覆盖并判为 FAIL，不使用“出现全部数字”代替事实绑定；这不是通用中文语义判断器。

报告含逐题实际计划/SQL/行集/回答、分项检查、执行次数、修复反馈证据以及差异路径。仅写本地演示数据和脱敏错误，不复制 .env、密钥或全部进程环境。

版本记录包含 suite/schema 版本、Git HEAD、dirty 状态、生产代码及评测器源文件哈希、数据/知识/模型脚本/预期哈希、Python/LangGraph/SQLite 版本。确定性结果摘要排除耗时、运行时间、随机 request_id；调用证据保留独立运行关联。

## 8. 指标、CLI 与退出码

报告列出总数、PASS/FAIL/ERROR 数、未完成数；业务指标分开给出分子分母和适用范围：

- 错误答案放行率：已交付答案中业务错误数 / 可判定的已交付答案数。
- 正确回答覆盖率：正确交付的可回答题 / 全部标注可回答题。运行错误不能通过移出分母美化覆盖率。
- 错误输入拦截率：在规定边界正确拦截的反例 / 可判定反例；运行错误和未判定数量另列。
- 误澄清率、需求覆盖和修复成功数按独立标注统计。分母为零时为 null/不适用，不能记 0%。
- 耗时与夹具调用次数单列，外部模型调用数恒为 0；不把夹具调用耗时说成真实模型性能。

拟定命令（实现后可用，目前不是已存在功能）：

```powershell
python -m smart_ask_data.evaluation --suite data/evaluation/m0/v1 --output artifacts/evaluation/m0-run-1
python -m smart_ask_data.evaluation --suite data/evaluation/m0/v1 --output artifacts/evaluation/m0-run-2 --compare artifacts/evaluation/m0-run-1/report.json
```

默认退出码：0 全部 PASS；1 存在业务 FAIL 且无 ERROR（仍生成完整报告）；2 存在运行 ERROR 或输入/依赖错误。当前基线有已知 FAIL 时返回 1 是有效业务测量，不代表评测工具测试失败。

默认不覆盖已有非空输出目录；不删除历史报告。支持只运行指定 case ID 时，报告标明部分评测，不能据此宣布整套通过。对比要求用例、数据、知识、模型脚本和预期指纹一致；代码指纹允许变化。输入不兼容时输出不可比较原因，不输出改进率。

## 9. 实现后验证与完成条件

1. 先为用例契约、判卷器和时钟输入写失败测试；证明错误日期、数字错配、重复行、负号丢失、全部拒答不会误判通过。
2. 加载完整 32 条用例，验证 ID 和快照引用；对主要数据独立手工核算并保存说明。
3. 从本地入口运行真实 LangGraph，不使用现有 FakeSemanticLLM 的字符串解析来构造标准答案，不走真实服务工厂。
4. 连续两次运行，稳定业务结果完全一致，包含每条已知失败；模拟不同宿主当天日期后结果不漂移。
5. 对比报告能识别指定用例从 FAIL 到 PASS、从 PASS 到 FAIL，以及夹具更改导致的不可比较；不通过修改正式业务节点制造交付假象。
6. 验证无网络调用、上下文不串题、资源关闭、故障替换恢复；依赖缺失不跳过。
7. 全量本地回归和基础静态检查通过；独立审查；保存真实生成的 JSON/Markdown 基线，更新 TODO。真实模型测试保持关闭。

本规格自审：32 条用例编号唯一；输入与预期独立；生产能力与评测能力分离；当前工作区基线与历史证据分离；费用、退出码、已知 FAIL 和 ERROR 处理已明确。实现及运行证据尚未产生，M0 不勾选完成。
