# M0：建立可复现的业务评测基线

状态：用户已批准启动需求开发与验证；需求和规格已整理，待规格审阅后进入代码实现。项目总需求仍以根目录 `需求理解.md` 为入口，本文是 M0 增量，不覆盖历史需求。

## 需求概述

为开发者提供一套固定、独立、可重复的业务考卷，评测 LangGraph 问数流程，记录当前问题并支持后续里程碑比较。不把程序自己的分数当成业务正确性证明。

## P0 功能需求

- [ ] 固定 SQLite 数据、表结构、参考日期、Asia/Shanghai 时区及知识版本，避免运行日期影响结果。
- [ ] 提供不少于 30 条带独立预期及核算依据的业务题和反例；首批设计为 32 条。
- [ ] 一条命令串行运行真实 LangGraph；模型使用固定响应夹具，每题独立数据库和状态。
- [ ] 分别判定计划要求、查询结果、答案事实绑定、停止原因及反馈修复；不以关键词或系统高分代替标准答案。
- [ ] 输出逐题 JSON/Markdown 报告及汇总指标，区分业务 FAIL 与运行 ERROR，保存版本指纹和可比较的基线。
- [ ] 测试评测器本身能抓住已知错误；相同快照重复执行产生相同业务判定。

## 非功能需求与边界

- 默认零外部模型调用，不加载真实凭据，不连接生产数据源，不新增依赖。
- 仅支持 LangGraph；不恢复备用执行器，不实现 SQL AST，不提前修复 M1—M6 的业务缺陷。
- 报告采用独立输出目录，禁止默认覆盖历史结果；不保存密钥或未经限制的环境信息。
- 当前基线明确为 M-1 修复后、单引擎工作区；保留历史证据，不伪造修复前运行。
- 不承诺真实模型质量、生产数据库集成效果或通用自然语言判卷能力。

## 验收标准

- 给定固定数据与时间，重复执行全部用例，预期与实际差异保持一致，耗时等非确定性元数据单列。
- 给定同一套独立标准答案，系统即使自评 100%，错日期、错数字绑定或负人数放行仍应判 FAIL。
- 给定无效夹具或缺失依赖，记录 ERROR 或启动失败，不能跳过后报告全部通过。
- 给定已知未修复业务缺陷，报告保存具体失败证据并关联后续里程碑，而不是修改预期让测试变绿。
- 给定不同代码版本及相同业务快照，可逐题比较改进/退化；业务快照不同则明确不可直接比较。
