## 1. 项目归类与改造边界

架构约束修订（2026-10-11）：LangGraph 为必需依赖和唯一工作流执行引擎；保留 `build_graph()`，移除 `ScoredWorkflow` 及导入失败时的自动切换。缺少 LangGraph 明确报错。此后 M-1/M0/M5 及共同验收均以单一 LangGraph 路径为准；旧双引擎测试与真实调用仅保留为历史证据。

项目定位为业务知识约束的智能问数应用：模型理解问题和提出计划，程序生成 SQL，只读查询引擎返回数据，系统组织答案并交付验证依据。本次属于应用运行阶段的可靠性改造，不涉及预训练、SFT 或 RL 训练。

保留现有指标知识、确定性 SQL 生成、查询引擎适配、分阶段节点和追踪基础。首轮围绕当前开户人数、交易金额及受支持维度形成闭环；不在验证改造中顺带承诺任意 JOIN、任意指标、多轮对话或复杂因果分析。

现状划为三类：

- **已有基础可复用**：结构化意图、候选检索、受知识约束的计划、SQL 生成、查询执行、确定性回答、逐轮记录。
- **已有校验需重构**：意图自评分、时间合法性检查、SQL 字符串检查、结果加权评分、答案数字集合检查、流程与报告的放行判断。
- **需要新增证据能力**：需求覆盖映射、元数据核对、数据完成水位、结果到结论的绑定、可执行业务评测。

| 分类 | 模块 | 要回答的问题 | 主要现有入口 |
|---|---|---|---|
| A | 意图与需求验证 | 是否完整理解用户要什么？ | `intent_recognizer.py`、`retrievability_validator.py`、`time_validator.py` |
| B | 业务知识与计划验证 | 选的指标和计算口径是否有依据？ | `qdrant_client.py`、`knowledge_validator.py`、`llm_planner.py`、`validator.py` |
| C | SQL 与执行验证 | 查询是否兑现计划，并符合访问与资源约束？ | `sql_generator.py`、`sql_executor.py`、`trino_client.py` |
| D | 数据与计算结果验证 | 返回的数据是否完整，计算关系是否成立？ | `result_validator.py`、指标知识文件 |
| E | 答案与证据验证 | 用户看到的文字、数值和限定条件是否忠实？ | `answer_generator.py`、服务响应及前端 |
| F | 决策、修复与追踪 | 哪些失败必须阻断，应回到哪里修复？ | `graph.py`、`state.py`、`service.py`、`trace_store.py` |
| G | 评测与质量治理 | 如何证明新机制比旧机制有效？ | `tests/`、待建业务评测集与运行入口 |

## 2. 对当前分数验证的准确判断

不能把当前机制统一描述成“分数足够就放行”。不同阶段的实际规则不同：

| 环节 | 当前实际决策 | 主要缺点 |
|---|---|---|
| 意图 | 检索目标、歧义、时间要求、模型置信度共同判断 | 模型自评不能证明没有漏掉或误解用户条件 |
| 知识 | 候选存在、分数达标、候选差距、定义完整共同判断 | 词法相关性不是业务口径正确性；原始候选分可超过 1 |
| 计划 | 检查项有失败就停止 | 仅检查选中候选、定义非空、保留下来的维度受支持；不能识别之前丢掉的要求 |
| SQL | 五项字符串检查有失败就重生成 | 硬拦截逻辑已存在，但检查内容不够强，错误 SQL 也可能五项全过 |
| 结果 | 部分关键失败或结果分低于 0.65 才重试 | 人数越界、分组缺失等可能被其他分项补偿 |
| 总分 | 取知识、时间、计划、SQL、结果分的最小值 | 这些数值既不同质也未校准；最小值仍不是答案正确概率 |
| 回答与 API | 回答节点内含 0.65 判断，服务层使用配置阈值 | 可能出现状态拒绝而正文仍交付数值的语义不一致 |
| 验证报告 | 部分阶段按 0.65 显示通过，计划阶段按失败项显示 | 与节点的真实放行标准不同；未执行也没有独立状态 |

原始检索匹配分、规则通过分、模型自评必须分别命名和解释。后续即使保留分数，也只用于候选排序、质量诊断和实验比较。需要经过独立评测及校准，才可以讨论概率含义。

## 4. 新验证机制的公共约定

### 4.1 检查记录与放行规则

拟统一检查记录字段：`check_id`、`requirement_id`（可为空）、`stage`、`subject`、`expected`、`actual`、`evidence_refs`、`status`、`severity`、`repair_target`、`rule_version`。

- 单项结论采用 `PASS / FAIL / UNKNOWN / NOT_APPLICABLE`。
- 阶段另记录 `NOT_RUN / RUNNING / COMPLETED`，避免把未运行当通过。
- 每种查询类型定义必需检查；必需检查 FAIL 或 UNKNOWN 时，不放行“已验证答案”。
- 可选检查 UNKNOWN 可以伴随结果展示，但必须披露，例如尚未与权威报表对账。
- 关键失败不可被其他分项抵消；模型复核没有权限豁免程序或权限检查。
- 检查产生结构化事实，统一决策器选择动作；API 与 UI 消费同一决策。

建议业务结果状态包括：已验证回答、需要澄清、能力不支持、数据不完整、访问/资源受限、执行失败。英文枚举及 API 兼容方案在 M1 定稿，不在本规划中直接改变现有接口。

### 4.2 需求和证据的传递

先固定用户需求及其来源，再建立需求到知识、计划、SQL、结果和答案的引用。业务默认值必须标记；没有覆盖的要求必须停止、澄清或明确交付部分结果，不能静默消失。

“原文包含某词”只能证明抽取出处，不能证明其业务解释正确；歧义必须结合指标知识与必要的用户反馈消解。内部引用一致也不能证明数据源本身正确，因此数据水位、独立样例及条件适用的对账仍需单独验证。

### 4.3 分数的保留与迁移

保留检索相关性分用于候选排序；保留规则统计用于调试；保留模型自评作为诊断信息。停止把未校准的分数呈现为“正确概率”。迁移期可暂保留原 `confidence` 字段以兼容客户端，但必须标记为旧规则分，不再决定新门禁；前端与后端成套验收后再讨论移除。

## 5. 里程碑与推进节奏

以下为依赖驱动的建议节奏，不是已承诺日历工期。每个里程碑完成后交付可演示场景、对应反例和评测对照；不以文件数量或平均分升高作为完成依据。

主线：M-1 → M0 → M1 → M2 → 调整后的 M3 → M4 → M5 → M6 → v1.1.0 验收发布。M-1 是最高优先级，不等待完整评测平台；M5 是基础验证阶段完成点，不等于 v1.1.0 完成；M6 按需模型复核须完成接入与收益验收，附加扩展不作为默认发布条件。

### M-1：反馈进入下一轮决策闭环（最高优先级）

实施进度（2026-10-11）：共享反馈修复节点及两套工作流接入已完成自动化验证；支持的修订范围为无效指标 ID（唯一知识候选）和重复分组。用户授权后的两项受控真实模型验收通过，M-1 在该限定范围内完成，不外推总体模型质量。详见 [M-1 实现记录](2026-10-11-M-1-反馈闭环实现记录.md)。下述目标和验收边界保持有效。

- **目标**：先解决用户指出的 ReAct 反馈未进入后续决策的问题，不再只执行原样 SQL 重试。
- **代码依据**：校验器写入 `retry_feedback`，但重试路由只回 `sql_generator`；该函数不读取反馈；规划器的模型输入也不包含反馈。这里是固定工作流的反馈消费缺口，不是前端 React 问题。
- **覆盖**：F03 基础、F04 最小轮次记录；从原 M5 前移。
- **交付**：请求内反馈/产物历史、下一轮真实模型入参注入、可恢复问题返回规划/修复决策、有效修订或停止、受影响检查重跑；原问题和业务约束保持不变。
- **验收**：在 LangGraph 中记录第二次模型调用，证明它包含前一轮错误、计划/SQL 和轮次；定向用例可修正或明确失败；首轮无反馈正常、不同请求隔离、同错误不无限循环。测试模型与真实模型效果分别报告。
- **边界**：一次自动修复预算；权限或数据缺失不靠模型猜测解决；生成器自身程序错误应报告，不靠原样重试；反馈是数据，不是可覆盖系统约束的指令。只检查输入、结构化修订及结果，不索取模型内部思维链。
- **节奏**：先保留修复前最小复现/请求证据，再实现闭环并做定向回归；M0 后续扩充完整基线并保留前后版本，M5 扩展覆盖和追踪。

### M0：建立可复现的评测基线

- **目标**：先让旧机制的问题能够被稳定测量。
- **覆盖**：G01、G02 的定义；B02 演示元数据快照；公共需求/检查结构草案。
- **交付**：固定 SQLite 数据快照、固定时钟和时区、知识版本、至少 30 条带独立预期的业务用例、LangGraph 批量评测入口和基线报告；固定模型响应作为输入，不充当标准答案。保留 M-1 修复前证据，明确当前工作区是修复后基线，不伪造历史版本实测。
- **用例组成**：正确查询、需求遗漏、时间边界、口径歧义、错误 SQL、空/零/异常结果、答案错配、修复及权限/资源边界；类别可交叉标注。
- **验收**：同一快照重复运行的逐题业务判定一致（耗时等运行元数据除外）；逐题能重现预期结果或错误；覆盖前期发现的四个反例；基线失败允许存在但必须被准确记录。仅评测 LangGraph 对业务标准是否正确，不再做双工作流一致性；必需依赖缺失直接失败。
- **节奏**：一个基础迭代。先形成测量能力，不同时铺开全部验证器。
- **边界**：模型固定响应的确定性回归与真实模型评测分别报告，前者不能宣称代表真实模型理解能力。

### M1：统一放行与结果展示

- **目标**：消除已知关键错误被分数补偿，以及执行/报告/正文相互矛盾的问题。
- **覆盖**：F01、F02、F04 骨架；D01 当前指标基础规则；E02 失败交付策略。
- **交付**：统一检查记录、阶段状态、决策入口、最小前端状态适配；开户人数等现有指标的硬失败规则。
- **验收**：负人数不能放行；SQL 被拒绝时 UI 同样拒绝；未执行节点不显示通过；必需检查未知时不能交付已验证数值。
- **依赖**：M0 的基线和接口草案。
- **节奏**：一个闭环迭代，包含 API 与 UI 联调，不只修改后端枚举。

### M2：需求理解与业务口径可核验

- **目标**：确认用户要求没有丢失，选用的业务定义有据可查。
- **覆盖**：A01—A03、B01—B03。
- **交付**：需求清单、固定请求时间与日历解析、指标 Schema、演示源元数据刷新、候选有效性检查、需求到计划的映射和澄清原因。
- **验收**：昨天解析错误被拦截；未知渠道不能被过滤后输出总计；歧义分母被澄清；非法知识定义无法加载；明确问题仍可直接回答。
- **依赖**：M1 的状态与决策机制。
- **节奏**：两个小迭代，先完成元数据/知识约束，再完成意图与计划的完整性验证。
- **边界**：没有渠道数据时返回不支持；本阶段不顺带扩建渠道业务数据和任意多指标分析。

### M3：SQL 基础校验与执行限制（AST 暂缓）

- **目标**：在声明支持的生成路径内维持基础检查，落实访问与资源限制，并明确 SQL 未验证边界。
- **覆盖**：C03/C04；C01/C02 的完整结构/语义实现暂缓，保留风险记录。
- **交付**：现有 SQL 检查回归、生成前计划/元数据约束、最小演示角色授权、只读执行、行数/超时/取消控制，以及 SQL 验证选型待办与范围说明；不交付 AST、不预设解析库。
- **验收**：支持范围内正确查询通过，已有拒绝检查无退化；授权失败不触发执行器；超时取消和结果截断有证据；反向条件/复杂绕过等未覆盖能力明确登记，不冒称已验证。
- **依赖**：M2 的计划与元数据；M1 的统一执行门禁。
- **节奏**：按保留的基础检查与执行约束重新拆分，不包含 AST 的实现工期。
- **边界**：暂不开放任意模型自由 SQL；现有子串检查、确定性生成或 EXPLAIN 不等于完整 SQL 正确性证明，LIMIT 不等于扫描成本受限。目标引擎须实测；无可验证安全边界的查询不执行。后续解析/语义方案需另行确认。

### M4：结果语义与答案证据闭环

- **目标**：结果可靠性和用户实际看到的答案一起验收。
- **覆盖**：D01 扩展、D02—D04 基础、E01—E02。
- **交付**：指标专属数值/空值规则、演示数据完成水位、结果完整性和派生值核对、事实记录及确定性关键字段渲染、来源与限制展示。
- **验收**：香港和上海数值不能调换；已完成分区无匹配记录可按指标规则回答零/无数据；未到齐分区不得冒充零；占比分母和派生值可复算；截断不能伪装完整。
- **依赖**：M2 的知识规则、M3 的执行元数据。
- **节奏**：两个小迭代，先数据条件及计算规则，再答案绑定和用户页面。
- **边界**：没有真实上游完成标记时，只能演示模拟水位接口，并明确真实新鲜度未知；权威报表、历史异常基线不假定已经存在。

### M5：修复增强与第一版验收

- **目标**：能修复可恢复问题，且不会为了通过检查改变用户目标。
- **覆盖**：在 M-1 已完成反馈闭环基础上扩展 F03、F04 完整、G02 发布评审；M-1 与 M0—M4 集成。反馈基础接入不能留到 M5 才做。
- **交付**：失败分类与路由、一次自动修复预算、修复变化记录、需求不变约束、下游重验、版本和耗时快照、全链路演示及评测报告。
- **验收**：LangGraph 中可恢复错误仅修复一次并成功或明确失败；永久错误不原样循环；数据未到齐不改写 SQL 碰运气；修复后所有受影响检查重跑。
- **依赖**：M2—M4 必须先能产生准确失败原因。
- **节奏**：一个修复迭代加一次集成验收。配置当前允许 2 次重试，而需求提出 1 次自动纠错，实施时按一次修复预算统一；暂时性传输重试单列且受总时限约束。
- **边界**：这是“验证机制第一版”验收，不能自动替代 `docs/TODO.md` 中容器化、新环境启动等其他项目验收。

### M6：按需模型复核与扩展收益评估

版本范围：按需模型复核属于 v1.1.0 必需交付；本节多候选、权威对账和历史基线属于可选扩展。必需的复核能力若未达到验收标准，应继续改进或另行确认范围变更，不能仅关闭功能便标记 M6 完成。

- **目标**：针对基础规则难以覆盖的复杂语义增加证据，并评估是否值得增加成本。
- **覆盖**：复杂意图/计划的模型复核；多候选比较；D04 权威对账和历史基线；G02 扩展实验。
- **交付**：按查询复杂度触发的评审、结构化异议与证据、适用范围明确的独立对账、额外调用预算及开关。
- **验收**：同一冻结评测集比较增强前后结果，记录错误放行、覆盖、误澄清、P95 耗时和调用成本；只有收益符合预先约定预算才启用。
- **依赖**：M5 稳定版本；权威报表需先核对口径、时间和版本。
- **边界**：模型不能自行降低验收标准；同模型多次输出相同答案不构成独立证明。复杂能力超出当前业务域时另立需求。

## 6. 每个里程碑都使用的验收约定

每个迭代按“列问题与失败用例 → 实现一个模块闭环 → 正反例验证 → 工作流/API/UI 集成 → 冻结结果并比较基线”的节奏推进。

发布候选必须满足以下确定性条件：

1. 当前里程碑负责的关键反例全部得到预期处理，已有硬门禁回归用例无失败。
2. 相应的正确用例同样通过，不把全面拒绝作为修复。
3. 校验结论、执行行为、响应状态和答案正文一致。
4. 每条问题编号都有实现位置、用例编号和验收记录；暂未实施项明确保留。
5. LangGraph 的分支、停止原因和最终语义符合独立业务预期；必需依赖缺失不能被备用执行器或测试跳过掩盖。
6. 验证报告区分“通过了哪些检查”和“仍缺什么证据”；不宣称覆盖任意 SQL 或全部现实数据问题。

真实模型的指标作为独立实验报告，不拿一次运行代替质量结论：

| 指标 | 计算口径 |
|---|---|
| 已放行答案错误率 | 放行但错误的题数 / 放行题数；无放行时记为不可计算，不能记为零 |
| 错误候选拦截率 | 被拦截的错误候选 / 已标注错误候选；基于反例集合单列 |
| 可回答覆盖率 | 正确回答的可回答题数 / 标注为可回答的题数 |
| 误澄清率 | 不需要澄清却请求澄清的题数 / 无需澄清的可回答题数 |
| 需求覆盖率 | 被正确兑现的必需需求项 / 必需需求项总数；不替代关键项硬门禁 |
| 修复有效性 | 修复成功数、修复机会数、引入新错误数分别报告 |
| 性能与成本 | 端到端及分阶段 P50/P95、数据库耗时、模型调用数与可取得的 token/费用 |

M0 完成后冻结真实模型实验的数值预算与允许回归范围，再评审候选改动。现有“普通问题尽量 30 秒完成”作为业务预算来源；需注明引擎和负载，不能把一次模型调用的超时当作整个请求的时间限制。
