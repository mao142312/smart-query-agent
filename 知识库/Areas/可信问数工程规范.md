# 可信问数工程规范

- 责任领域：指标知识治理、查询安全、结果可靠性、可解释性
- 最后更新：2026-08-16

## 核心原则

1. 知识库决定“查什么”：指标含义、来源表、公式、时间字段、强制过滤和允许维度必须来自受控知识定义。
2. 模型决定“如何理解和表达”：LLM 可以生成结构化计划和自然语言答案，但不能修改指标口径或跳过验证。
3. SQL 必须逐轮校验：每次生成或重试都保存 SQL、规则得分、执行结果和失败原因。
4. 结果必须独立评分：SQL 正确不等于数据结果可靠，仍需检查执行、非空、完整性、业务范围、维度和新鲜度。
5. 严重问题不能被平均分掩盖：综合可信度取知识、计划、SQL、结果分数中的最低值。
6. 证据不足时拒答：低于阈值或重试耗尽时返回 `unreliable`，不将结果包装成可靠指标。

## 当前评分依据

### 语义计划

- 指标唯一匹配。
- 指标定义包含来源表、公式和强制过滤。
- 时间范围完整。
- 请求维度属于知识库允许范围。

### SQL

- 单条只读 `SELECT`。
- 只访问指标指定的白名单表。
- 包含知识库要求的全部强制过滤条件。
- 包含时间范围和返回行数限制。
- 输出统一的 `value` 指标列。

### 查询结果

- SQL 成功执行。
- 结果非空。
- 每行指标值非空。
- 当前基础规则要求数值非负。
- 分组结果包含计划要求的维度。
- 查询结束日期不得晚于当前日期。

## 已知评分边界

- 当前“新鲜度”只验证查询日期，不代表真实数据分区已经更新。
- 非负检查只是通用下限，不能替代每个指标的业务合法范围。
- 尚未引入历史波动基线与权威报表对账。
- 当前知识检索和数据源均为 Mock，因此 100% 只表示 Demo 规则全部通过，不表示生产数据绝对正确。

## 变更要求

- 新增指标时必须同时增加知识定义、Mock/测试数据和自动化测试。
- 修改评分项或权重时必须记录版本、理由和预期影响。
- 修改答案生成逻辑时必须验证答案中的所有数值均能在查询结果中找到依据。
- 真实环境不得在代码库、日志、前端响应或本文档中暴露密钥。
